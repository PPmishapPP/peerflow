# PeerFlow — бизнес-описание

Версия: 2.0
Обновлено: 20.11.2026

Этот документ описывает **что** делает PeerFlow и **по каким правилам**, языком
бизнеса. Здесь нет технических деталей: как это устроено в коде — в
[`architecture.md`](architecture.md), что и в каком порядке делаем — в
[`plans/`](plans/).

**Как пользоваться.** Каждое правило помечено идентификатором вида `BR-LEGIT-3`
(BR = Business Rule). Ссылайтесь на эти ID в планах и в описании системы — так
видно, к какому требованию относится код. Если меняете правило — меняйте его
здесь и обновляйте ID.

---

## 1. Зачем это нужно

PeerFlow — приложение для сообщества, у которого **нет постоянного лидера**.
Власть исполнителя здесь не постоянная: сообщество выдаёт её на время конкретной
задачи и может отозвать в любой момент. Сообщество вместе решает, **что** делать,
**кто** будет исполнять и **достаточно ли хорошо** исполнено.

**Цель проекта:** реальный продукт для собственного сообщества. Важны надёжность,
приватность, защита от спама и злоупотреблений.

### Какие проблемы решаем

| ID | Проблема |
|---|---|
| `BR-PROB-1` | В мессенджере всегда есть создатель чата, и он получает власть просто за то, что создал чат: может забанить, не пригласить, удалить чат целиком |
| `BR-PROB-2` | Много спама |
| `BR-PROB-3` | Слышно самых крикливых, а не самых умных |
| `BR-PROB-4` | Нет контроля за выполнением принятых решений |

### Как решаем — коротко

| ID | Правило |
|---|---|
| `BR-OVER-1` | Создатель сообщества не получает дополнительных прав за создание |
| `BR-OVER-2` | Любой член сообщества может внести предложение |
| `BR-OVER-3` | Под предложением идёт дискуссия, устроенная так, что не превращается в спам-чат |
| `BR-OVER-4` | По итогам обсуждения сообщество решает: делаем или нет |
| `BR-OVER-5` | Выбирается **ситуативный лидер** — человек, отвечающий за выполнение |
| `BR-OVER-6` | Лидер получает исполнительную власть на время этой задачи и может распоряжаться её бюджетом |
| `BR-OVER-7` | Лидер публикует отчёты о ходе работы; под отчётами тоже идёт дискуссия |
| `BR-OVER-8` | После выполнения лидер получает репутацию, видимую рядом с аватаром |
| `BR-OVER-9` | Выполнено ли задание — решает сообщество голосованием; лидер лишь запускает процедуру закрытия |

## 2. Три сущности власти (ядро модели)

Это центральная часть. Три сущности **независимы** друг от друга: право голоса,
легитимность и репутация — разные вещи.

### 2.1. Право голоса

| ID | Правило |
|---|---|
| `BR-VOTE-1` | Есть у каждого члена сообщества |
| `BR-VOTE-2` | Фиксированное: один человек — один голос |
| `BR-VOTE-3` | Неотчуждаемое: нельзя передать и нельзя потерять |

Право голоса используется, чтобы:

| ID | Применение |
|---|---|
| `BR-VOTE-4` | Решить «делаем / не делаем» |
| `BR-VOTE-5` | Оценить выполнение задачи |
| `BR-VOTE-6` | Оценивать сообщения реакциями «плюс / минус / спам» |
| `BR-VOTE-7` | Утвердить бюджет предложения |
| `BR-VOTE-8` | Принять нового члена в сообщество |

### 2.2. Легитимность

| ID | Правило |
|---|---|
| `BR-LEGIT-1` | Это исполнительный мандат (исполнительная власть), не связанный с правом голоса напрямую |
| `BR-LEGIT-2` | Каждый член обладает своей легитимностью и может добровольно передать её кандидату |
| `BR-LEGIT-3` | Работает **по каждой задаче независимо**: по разным задачам можно поддержать разных кандидатов |
| `BR-LEGIT-4` | Кандидат, собравший больше всех легитимности, становится лидером и получает право выполнять задачу и распоряжаться её бюджетом |
| `BR-LEGIT-5` | Любой член может в любой момент **вернуть свою легитимность** себе |
| `BR-LEGIT-6` | Если лидер теряет слишком много легитимности — мандат прекращается и выбирается новый лидер |

### 2.3. Репутация

| ID | Правило |
|---|---|
| `BR-REP-1` | Лидер получает репутацию при закрытии задачи: вся оставшаяся у него легитимность переходит в репутацию |
| `BR-REP-2` | Видна рядом с аватаром |
| `BR-REP-3` | Основное назначение — витрина достижений |
| `BR-REP-4` | Единственное рабочее применение — тай-брейкер при выборе лидера, если кандидаты набрали одинаковую легитимность |

## 3. Дискуссия и ранжирование

Под предложением и под отчётом лидера члены ведут дискуссию в виде сообщений.

> **Важно не путать две разные шкалы:**
> реакция на сообщение — «плюс / минус / спам»; голос по решению — «за / против».

### 3.1. Сообщения и реакции

| ID | Правило |
|---|---|
| `BR-DISC-1` | Член сообщества пишет аргумент (сообщение) |
| `BR-DISC-2` | Другой член ставит одну реакцию: **плюс** (по делу и согласен), **минус** (по делу, но не согласен), **спам** (не по делу) |
| `BR-DISC-3` | Можно писать сообщение в ответ на другое сообщение — вложенные ветки |

### 3.2. Ранжирование сообщений

| ID | Правило |
|---|---|
| `BR-DISC-4` | Сортировка «Популярные»: больше плюсов — выше; минусы понижают при равенстве плюсов |
| `BR-DISC-5` | Сортировка «Новые»: по времени создания, чтобы свежее не тонуло под старым |
| `BR-DISC-6` | Логика всплытия и скрытия спама действует и внутри веток, вложенно |

### 3.3. Ранжирование предложений в списке

| ID | Правило |
|---|---|
| `BR-RANK-1` | Чем живее и поддержаннее обсуждение, тем выше предложение |
| `BR-RANK-2` | Метрика популярности: **число уникальных участников + перевес голосов (за − против)** |
| `BR-RANK-3` | Объём сообщений популярность **не** повышает: иначе громкое и бессмысленное вылезает наверх за счёт количества |
| `BR-RANK-4` | Список можно сортировать: по популярности, по размеру бюджета, по новизне |
| `BR-RANK-5` | Предложения разделены на секции: «В работе» (решение принято, есть лидер и бюджет) и «На обсуждении» |

## 4. Жизненный цикл предложения

| ID | Шаг |
|---|---|
| `BR-LIFE-1` | Член сообщества вносит предложение и **обязательно указывает бюджет** |
| `BR-LIFE-2` | Идёт дискуссия |
| `BR-LIFE-3` | Параллельно выдвигаются кандидаты в лидеры, им можно сразу передавать легитимность |
| `BR-LIFE-4` | Голосование «делаем / не делаем», одновременно утверждается бюджет. Правило: простое большинство от проголосовавших. Минимальный кворум не требуется |
| `BR-LIFE-5` | При положительном решении лидером становится кандидат с наибольшей легитимностью |
| `BR-LIFE-6` | Лидер получает исполнительный мандат и доступ к бюджету задачи |
| `BR-LIFE-7` | Лидер публикует отчёты: отчётом считается любой прикреплённый файл или написанное сообщение, отдельного формата нет |
| `BR-LIFE-8` | Лидер запускает процедуру закрытия задачи |
| `BR-LIFE-9` | Сообщество голосует «выполнено / нет»; при закрытии оставшаяся легитимность лидера переходит в репутацию |
| `BR-LIFE-10` | Если легитимность лидера падает ниже порога — мандат прекращается; сообщество заново решает, продолжать ли задачу, и при «да» назначает нового лидера и новый бюджет |

---

## 5. Бюджет

| ID | Правило |
|---|---|
| `BR-BUDGET-1` | В MVP бюджет **виртуальный**: это учёт, а не касса |
| `BR-BUDGET-2` | Автор указывает бюджет при создании предложения |
| `BR-BUDGET-3` | Бюджет утверждается сообществом при голосовании |
| `BR-BUDGET-4` | Лидер может «тратить» бюджет задачи; траты записываются |
| `BR-BUDGET-5` | Отдельного формата отчётности по тратам нет: файлы и сообщения лидера и есть отчёт |
| `BR-BUDGET-6` | Реальных переводов денег, платёжной интеграции и эскроу **нет** — это отдельная фаза после MVP |
| `BR-BUDGET-7` | Если мандат утрачен, а задачу решили продолжить, бюджет назначается заново |

## 6. Легитимность и выбор лидера

### Как выбирается лидер

| ID | Правило |
|---|---|
| `BR-LEADER-1` | Пока идёт дискуссия, любой член может выдвинуть свою кандидатуру |
| `BR-LEADER-2` | Кандидатам можно сразу передавать легитимность |
| `BR-LEADER-3` | Как только принято «делаем», лидером становится кандидат с наибольшей легитимностью |
| `BR-LEADER-4` | Тай-брейкеры по порядку: больше легитимности → больше репутации → раньше вступил в сообщество |

### Когда лидер утрачивает мандат

| ID | Правило |
|---|---|
| `BR-LEADER-5` | Порог удержания: если лидер теряет больше 30% изначально переданной легитимности (остаётся меньше 70%) — мандат утрачен |
| `BR-LEADER-6` | Отзыв легитимности — конфликтное и смелое решение, значит лидер сделал что-то не так |
| `BR-LEADER-7` | После утраты мандата сообщество заново решает, продолжать ли задачу |
| `BR-LEADER-8` | Легитимность по каждой задаче независима: по одной задаче можно поддержать одного, по другой — другого |

## 7. Спам и защита от сговора

| ID | Правило |
|---|---|
| `BR-SPAM-1` | Метка «спам» скрывает сообщение, когда её поставили 3 или более участников |
| `BR-SPAM-2` | Защита от сговора (группа массовыми метками скрывает неудобное) в MVP **не реализуется** — известный вектор, ждём реального кейса |

---

## 8. Вход в сообщество

| ID | Правило |
|---|---|
| `BR-JOIN-1` | Аутентификация: логин и пароль |
| `BR-JOIN-2` | Один сервер обслуживает одно сообщество; человек не может состоять в нескольких |
| `BR-JOIN-3` | Первый зарегистрировавшийся попадает в сообщество автоматически |
| `BR-JOIN-4` | Следующий регистрируется, заполняет «о себе», прикрепляет фото и нажимает «вступить» |
| `BR-JOIN-5` | Члены сообщества должны его принять: нужно минимум 30% голосов за приём |

## 9. Пороги, приватность и осознанные риски MVP

### Пороги (для MVP — постоянные значения системы)

| ID | Порог |
|---|---|
| `BR-LIMIT-1` | Удержание легитимности лидером: потеря более 30% (остаток ниже 70%) |
| `BR-LIMIT-2` | Скрытие сообщения как спама: 3 метки |
| `BR-LIMIT-3` | Приём нового члена: минимум 30% голосов за |

В будущем пороги можно будет менять через предложение (самоуправляемая настройка)
— `BR-LIMIT-4`.

### Приватность

| ID | Правило |
|---|---|
| `BR-PRIV-1` | Сообщества приватные: контент виден только участникам |
| `BR-PRIV-2` | Удалённый аккаунт не стирается физически, а помечается как удалённый |

### Риски, принятые осознанно

| ID | Риск |
|---|---|
| `BR-RISK-1` | Решение принимается большинством от проголосовавших, минимальный кворум не требуется. Значит, в малолюдном сообществе решение может пройти голосами одного человека. Это главный вектор атаки, принятый как временное упрощение |

---

## 10. Чего в MVP сознательно нет

- Реальных денег, эскроу, платёжной интеграции (`BR-BUDGET-6`).
- Push-уведомлений.
- Деплоя и CI/CD.
- Защиты от сговора массовыми метками (`BR-SPAM-2`).
- Обязательного кворума при голосовании (`BR-RISK-1`).
