# Правила проекта PeerFlow

Это рабочие правила для всех задач в репозитории. Они действуют всегда и для
любого агента. Читай их перед началом работы.

## Два живых документа и планы

| Документ | Что описывает | Кто ведёт | Язык |
|---|---|---|---|
| [`docs/peerflow.md`](docs/peerflow.md) | **Бизнес:** что делаем и по каким правилам | Бизнес-аналитик | Бизнес-язык, без техники |
| [`docs/architecture.md`](docs/architecture.md) | **Как система устроена сейчас** | Агент | Технический |
| `docs/plans/*.md` | Что и в каком порядке делаем | Агент → ревью | Технический |

- `docs/peerflow.md` — **источник правды по продукту.** Каждое правило имеет
  идентификатор `BR-…`. Никаких технических деталей здесь быть не должно.
- `docs/architecture.md` — описание **фактического** состояния системы, со
  ссылками на ID требований. Только «как есть», никаких «планов на будущее».
- Планы — одноразовые: сделали и убрали в `docs/plans/completed/`.

## Рабочий процесс

1. **Бизнес-аналитик** правит [`docs/peerflow.md`](docs/peerflow.md): новое или
   изменённое требование получает ID `BR-…`.
2. **Агент** читает `docs/peerflow.md` и `docs/architecture.md`, составляет план
   в `docs/plans/yyyymmdd-<тема>.md`. План ссылается на ID требований.
3. **Технический специалист** проверяет план. Это самый дешёвый этап для
   правок — ошибку лучше поймать здесь, а не в коде.
4. **Агент** реализует план по задачам, каждая задача заканчивается тестами.
5. **Технический специалист** делает ревью результата.
6. **Агент** обновляет [`docs/architecture.md`](docs/architecture.md) (как
   устроено теперь) и переносит план в `docs/plans/completed/`.

## Задача не закрыта, пока…

- не написаны и не проходят тесты на новый и изменённый код;
- не обновлён [`docs/peerflow.md`](docs/peerflow.md), **если изменилось поведение
  или правило** — правим в той же задаче, не откладывая;
- не обновлён [`docs/architecture.md`](docs/architecture.md) под фактическое
  состояние — таблицу «что где лежит» и трассировку «требование → код»;
- в плане не отмечен прогресс (`[x]` — сделано, `[+]` — новая задача,
  `[!]` — блокер).

Расхождение кода и документов считается дефектом, а не мелочью.

## Структура репозитория

```
peerflow/
├── AGENTS.md              — этот файл, правила работы
├── README.md              — точка входа, карта проекта
├── docs/
│   ├── peerflow.md        — бизнес-описание (источник правды по продукту)
│   ├── architecture.md    — как система устроена сейчас
│   └── plans/             — планы реализации (текущий + completed/)
├── backend/               — сервер: Java 21 + Spring Boot
├── android/               — приложение: Kotlin + Jetpack Compose
├── presentation/          — слайды
```

## Технологии и ограничения

- Бэкенд: Java 21, Spring Boot 3.x, Gradle, PostgreSQL, Flyway, JPA/Hibernate,
  JUnit 5 + Testcontainers.
- Клиент: только Android, Kotlin + Jetpack Compose.
- Перед написанием кода сущностей JPA — активировать навык `spring-data-jpa` и
  следовать его правилам; при отклонении сначала спросить разработчика.
- Держаться рамок MVP: без реальных денег и эскроу, без push-уведомлений, без
  деплоя и CI/CD, без защиты от сговора и без обязательного кворума — это
  осознанно отложено (см. `docs/peerflow.md`, раздел 10).

## Команды

```powershell
# Приложение
cd android; .\gradlew.bat :app:assembleDebug
cd android; .\gradlew.bat :app:testDebugUnitTest

# Сервер
cd backend; .\gradlew.bat test
cd backend; .\gradlew.bat bootRun --args="--spring.profiles.active=local"
```

В `backend/src/main/resources/application.yml` прописаны рабочие умолчания для
локальной разработки (`jdbc:postgresql://localhost:5432/peerflow`, пользователь
`usr`). Свои значения задаются в `backend/src/main/resources/application-local.yml`
(файл в `.gitignore`, шаблон — `application-local.yml.example`) или переменными
`PEERFLOW_DB_URL`, `PEERFLOW_DB_USERNAME`, `PEERFLOW_DB_PASSWORD` — подробности
в [`backend/README.md`](backend/README.md).
